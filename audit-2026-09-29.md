## Recommendation

Use one **Notebook** navigation destination plus **About**. Show all entries in one chronological archive, with optional Notes and Projects filters. Keep current `/writing/*` and `/projects/*` detail URLs during the first iteration. A navigation change does not require a route migration.

Writing and Projects can serve different purposes: an article explains an idea or lesson; a project records a thing's purpose, operation, progress, and outcome. In this checkout, however, there are only three published articles and one project. “This Website” and “Building This Site” repeat the motivation and stack without linking to each other. The distinction currently adds navigation more than value.

Initially, keep one substantive website article and turn the project page into a short overview linking to it, or integrate both into one case study with a compatibility page at the old URL. Do not silently remove an existing URL. Keep the two internal collections until there is a reason to migrate their data; one reader-facing archive does not require one schema.

## Redundancy and maintenance

- **Repeated homepage entry:** `src/pages/index.astro:8–9` independently selects featured and recent posts. “Building This Site” appears in both sections. Exclude featured entries from recent, or use one list with a featured marker.
- **Separate project previews:** homepage and project archive implement their own markup/CSS and already show different metadata. Extract a shared ProjectCard if projects remain separately presented.
- **Unused project metadata:** project `featured`, `updated`, and `tags` are accepted but not used in the current project presentation/discovery. Implement their meaning or remove them. Tags and RSS currently cover only blog posts, so projects do not join topic browsing.
- **Duplicated origin:** the production URL is maintained in both `astro.config.mjs` and `src/lib/site.ts`; robots and CNAME also need consistency checks when moving domains. Make the generated metadata origin authoritative in one place.
- **Repeated styles:** archive page headers, metadata rows, tags, and status badges repeat across routes. Extract a few shared components/styles after settling navigation; avoid a large abstraction rewrite.
- **Duplicate asset:** `public/assets/keep_learning.svg` and `favicon.svg` have identical SHA-256 hashes; the former has no source references found.
- **Unused MDX capability:** all five content files are Markdown. Consider removing MDX if interactive content is not planned; retain it deliberately if that capability is useful.
- **Formatting drift:** the existing `format:check` command reports 34 files. Handle normalization in its own change so functional diffs stay reviewable.

## Performance and authoring

- The header loads a **1,179,333-byte PNG** to display at 32×32 pixels. Generate small appropriately sized logo variants and a separate touch icon. This is the clearest asset optimization.
- `BaseHead.astro` requests four Google font families and multiple weights. Lora is only a fallback behind Fraunces. Reduce the set and consider self-hosting the chosen fonts.
- `Dots.astro` uses a fixed full-window canvas, so the animation appears behind the entire homepage, not just the hero. Initial reduced-motion preference is respected, but live preference changes are not watched; colors do not update on OS theme changes unless `data-theme` changes. Constrain the effect or remove it if reading is the priority.
- The theme icon behavior does not match its “theme you'd switch TO” comment, and does not follow the system-dark CSS path consistently. Align the icon and accessible label with one documented behavior.
- `scripts/new-post.mjs` escapes quotes but not backslashes when producing YAML; Windows paths or escape-like text can corrupt content. Bare tags such as `true` can become YAML booleans, and `a: b` can become mappings. Use proper scalar serialization. Reject empty generated slugs, blank descriptions, and invalid project status before writing; use exclusive file creation.
- Archive cards always render `h3`, including routes where they directly follow `h1`. Use heading levels appropriate to the parent context.
- `.gitignore` ignores only `.env` and `.env.production`; add other local environment variants with an explicit exception for a safe example file. No matching common private-key/token patterns were found in the scanned current source. This was not a full-history secret scan.
